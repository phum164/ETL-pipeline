01 · โมเดลการขาย

Grain สำคัญ: ออเดอร์หนึ่งแถว ≠ สินค้าหนึ่งชิ้น และยอดทั้งบิล ≠ รายได้รายการสินค้า เส้น FK ที่ไปวันมีสองบทบาท: วันสั่งซื้อและวันส่งถึงลูกค้า

สินค้าและหมวดอยู่ที่ใด?

ไม่มี dim_product หรือ dim_category แยกต่างหาก ชื่อ/รหัสสินค้า หมวด สี/คุณลักษณะ และขนาดอยู่ใน dim_sku แบบข้อมูลปัจจุบัน ไม่ใช่ประวัติหมวดตอนขาย และไม่ roll up ตามต้นไม้หมวด

ส่งถึงลูกค้าและคืนสินค้า

ใช้เหตุการณ์ DELIVERED หรือ COMPLETED เฉพาะ POS ตาม transform กลาง ยอดส่งถึงยังคงเป็นยอดขั้นต้นเมื่อภายหลังคืน/ยกเลิก วันที่รับคืนเก็บที่ fact_order.return_received_at แต่ยังไม่มี fact คืนสินค้าระดับ SKU / จำนวนชิ้น / มูลค่าคืน

02 · โมเดล Social Commerce

การจอง การชำระ และสถานะเป็นหลักฐานคนละ grain ETL รวมเป็น current snapshot สำหรับออเดอร์ Facebook ที่มี reserve/CF แล้ว API จึงประเมินการจ่ายภายในกำหนด

24 ชั่วโมง และนิยาม CF ในโค้ดปัจจุบัน

cf_at สร้างจาก earliest_due_at − 24 hours ไม่ใช่คัดลอก created_at ของ reserve แรกโดยตรง ต้องมี due ครบและตรงกัน และ due ไม่น้อยกว่าเวลา reserve แรก + 24 ชั่วโมง หากหลักฐานไม่ผ่านเงื่อนไข เวลา CF/due อาจว่างและถูกจัดเป็นข้อมูลไม่ครบ

ฐานอัตรา CF แล้วไม่จ่าย

API กรองตามวันไทยของ cf_at และใช้ cutoff ของ ETL ที่โหลดสำเร็จ ไม่นับ COD หรือข้อมูลไม่ครบในตัวหาร การยกเลิกที่พ้นกำหนดยังอาจอยู่ในกลุ่มไม่จ่าย ข้อมูลที่ยังไม่ถึงกำหนดแยกจากกลุ่มพ้นกำหนด

03 · โมเดลสต็อก

Movement เก็บการเปลี่ยนแปลง ส่วน snapshot เก็บค่าที่จับได้ในแต่ละวัน การรันซ้ำในวันเดียวอัปเดต grain เดิม ไม่สร้างประวัติหลายเวลาภายในวัน และ snapshot เก่าที่ไม่มีหลักฐานต้นทางไม่สามารถสร้างย้อนหลังได้ครบ

04 · สายที่มาของ mart และผู้ใช้ข้อมูล

ลูกศรส่วนนี้แสดง lineage ไม่ใช่ FK ชุด input ทางซ้ายเป็นการย่อกลุ่มตารางเพื่อให้อ่านง่าย ไม่ได้สร้างตารางหรือ abstraction ใหม่ ใน API ปัจจุบันมี direct consumer ของ 6 views ส่วนอีก 4 views ยังไม่มีผู้เรียกโดยตรงใน AnalyticsService

มูลค่าที่ใช้ไม่ใช่ยอดเดียวกัน

รายวันระดับออเดอร์ใช้ total_amount ขณะที่รายได้หมวด/สินค้า/SKU ใช้ line_subtotal_amount หลังส่วนลดรายสินค้า ก่อนคืนสินค้า และไม่รวมส่วนลดทั้งบิล ค่าขนส่ง หรือภาษี จึงไม่ควรบังคับให้สองฐานนี้เท่ากัน

ยอดคืนสินค้าเป็น delivery cohort

v_sales_daily นับออเดอร์ที่มี return_received_at ตามวันส่งถึงลูกค้า ไม่ใช่วันที่คืนจริง ส่วนยอดส่งถึงใน buyer/province mart กลับจัดกลุ่มตามวันสั่งซื้อ

หมวด/สินค้าไม่ระบุยังมีรายได้

หมวดที่ไม่ระบุมี label สำหรับแสดงผล รายได้ที่ product ID ว่างยังคงอยู่ใน composition และไม่ควรถูกตัดออกเพื่อให้กราฟดูครบ SKU แต่ละ source ID แยกกันแม้ชื่อ/รหัสซ้ำ

ข้อแตกต่างของ province mart

v_sales_province_daily รวมทุกช่องทาง และการนับ distinct buyers ไม่ได้ใช้ตัวกรองยกเลิก/ลบเดียวกับยอดขาย ในปัจจุบัน API top provinces อ่าน v_sales_buyer_daily แทน พร้อมเงื่อนไขของ API
